1需求分析

1.1 核心问题陈述

screenshot-to-code 原项目的能力是「单张截图 → 单栈代码」。fork 要补上的是「真机多屏采集 → 批量多栈生成 → 渲染验证闭环」这条全链路。当前卡点不是生成能力（已有 6 栈 + 火山引擎 vision），而是没有一份干净的数据集来喂生成、做评测、做回归。

本质上这是一个数据工厂项目：采集管线产出高质量 UI 三元组（截图 + UI 树 + 骨架），生成管线消费它产出代码，验证管线回采渲染截图做比对——三者形成自循环飞轮。

1.2 利益相关者与场景

开发者（自用）从真机一键采集 → 批量生成代码 → 验证质量部分 采集已跑通，生成已有，验证缺自动化
研究者（国产模型）产出 ⟨s, a, s'⟩ 三元组 + 指令数据，训练/评测国产 GUI 模型未开始 数据碎片化，无跨 run 记忆
产品验证给定截图，生成 6 栈代码并验证可编译/可渲染部分 5/5 栈生成 PASS，XML 真机 PASS，Compose 阻塞

  • 像素/骨架/语义三层比对
  • HTML 栈：浏览器直接渲染

  • Compose 栈：Compose Driver / CLI 直编
  • QML/A2UI/WinUI3 栈：各自验证器

D 段 · 数据工厂

  • 低阶指令 → 高阶任务合成

3.4 关键架构决策记录（ADR）

ADR-001: 单文件自包含遍历器

决策：遍历器核心逻辑全部在 adb_traversal.py（1528 行），不拆包。

理由：worktree 部署简单；双杀软环境下减少文件 I/O；方便设备端调试。

代价：文件偏大，但函数边界清晰（7 个 class + 20 个函数），pyright 0 errors。

复审：B 段引入 LLM 感知层时应拆出 llm_perception.py，避免单文件膨胀超过 2000 行。

ADR-002: 原生 dump 优先 + u2 可选

决策：try: import uiautomator2; except: u2 = None，缺失时静默降级。

理由：机顶盒定制 ROM 推 atx-agent 风险高；零侵入是硬约束。

代价：原生 dump ~2.9s vs u2 ~0.17s（17×）；但当前步均 20.7s 中 dump 只占 14%，瓶颈在 screencap+pull。

ADR-003: 按目标包 seed 而非从 launcher 全量

决策：--package com.device.settings 分别 seed 各目标 App。

理由：launcher 签名不稳定（卡片轮播/侧边栏 DOM 变），DFS 从 launcher 出发 depth 预算被 help 链吃光。

代价：跨 App 跳转链路丢失（launcher→settings→help 等），需 global UTG 补回。

ADR-004: CLI 直编绕 Gradle 死锁

决策：kotlinc 2.0.21 + compose-compiler-plugin → d8 → aapt2 link → 合并 dex → zipalign → apksigner。

理由：360+Defender 拦截 native instrumentation agent，Gradle 8.9/8.11.1 daemon 均冻结。

代价：KMP 元数据 jar 陷阱（需手动选 -jvm 变体）；build 脚本维护成本高。

复审：Gradle 问题修复后应回退到标准构建；Compose Driver（L1）可作为无设备验证的长期方案。

ADR-005: 结构签名 + pHash 双通道去重

决策：主通道 = 结构签名（class|resource-id|归一化 text|desc → MD5）；第二通道 = pHash（imagehash，768px JPEG，汉明距离 ≤ 8）。

理由：ICSE'20 结论——没有单一算法能抓住所有功能近重复；结构签名盲区是「布局同、内容异」（如列表不同数据页）。

代价：新增 imagehash 依赖（MIT，轻量纯 Python）。

4.2 待建模块详细设计

4.2.1 GlobalUTG（跨 run 状态图）

目标：把多次 run 的 graph.json 合并成 global_graph.json，遍历启动时加载——已探过的边直接复用签名，不重复探索。

接口设计：

# backend/scripts/global_utg.py（新建）
class GlobalUTG:
    def __init__(self, path: Path): ...
    def load(self) -> dict: ...
    def merge_run(self, run_graph: dict) -> int:
        """合并一个 run 的 graph.json，返回新增 state/edge 数"""
    def has_state(self, sig: str) -> bool: ...
    def has_edge(self, from_sig: str, action_key: str) -> Optional[str]:
        """已知边的 to-state 签名，避免重复探索"""
    def save(self) -> None: ...
    def export_element_docs(self) -> list[dict]:
        """UTG 边 → 元素文档初版（无需 LLM）"""

合并规则：

  • state 去重：结构签名相同 → 合并（保留更丰富的 actions/texts）
  • edge 去重：from-sig + action.key 相同 → 合并（保留 effective 导航法）
  • Consolidation：同一元素跨 run 出现 → 取最新 action_effect

工作量：~1 天，纯工程，无外部依赖。

4.2.2 SoMExporter（Set-of-Mark 标注导出）

目标：把每个 state 的 actions + bounds 渲染为带数值标签的 screenshot_som.jpg。

接口设计：

# backend/scripts/som_exporter.py（新建）
class SoMExporter:
    def export(self, screenshot_768: Path, actions: list[Action],
               out_path: Path) -> Path:
        """在 768px JPEG 上画框 + 编号，产出 screenshot_som.jpg"""
        # Pillow: ImageDraw.rectangle + text
        # 编号 = action 在 actions 列表中的 index
        # 颜色编码: clickable=绿, focusable=蓝, scrollable=橙

用途：a) 给 LLM 代码生成用（模型指认「组件 3 是 Grid」比给坐标可靠）；b) 给验证器做语义走查对齐基准。

工作量：~半天，Pillow（已有），无新依赖。

4.2.4 LLMExplorer（LLM 引导探索）

目标：--strategy llm 模式，LLM 对候选 Action 打分（未访问优先 + 语义价值），动作后 LLM 判断「状态变化是否符合预期」。

接口设计：

# backend/scripts/llm_explorer.py（新建）
class LLMExplorer:
    def __init__(self, backend: AdbBackend, llm_router, cfg): ...
    def score_actions(self, actions: list[Action], state_meta: dict,
                      som_path: Path) -> list[tuple[Action, float]]:
        """LLM 对候选动作打分，返回排序后的 (action, score)"""
    def reflect(self, before_som: Path, after_som: Path,
                action: Action) -> dict:
        """动作后反思：状态变化是否符合预期 → 预筛 action_effect"""

复用来源：DroidRun Manager/Executor 编排（MIT, L2）+ Mobile-Agent-v3 多角色 prompt（MIT, L3）。

模型：百炼 glm-5.2 / 火山 doubao-seed-2-1-turbo（已有 key），不需要 GUI-Owl。

工作量：中，需调 prompt + 接 LLM API。

4.2.5 ElementDocLibrary（元素文档库）

目标：UTG 边 ⟨s, a, s'⟩ 蒸馏成 AppAgent 式元素文档，注入生成 prompt + 下次遍历跳过死路。

文档 schema：

{
  "element_id": "settings_btn_3",        // bounds + class 哈希
  "element_type": "TextView",
  "visual_description": "设置入口按钮",    // LLM 生成或从 texts 提取
  "bounds": [950, 390, 2890, 1770],
  "action_effect": "进入设置列表页",      // from to-state texts 摘要
  "from_state_sig": "39938a6c...",
  "to_state_sig": "a1b2c3d4...",
  "confidence": 0.85,                    // LLM 反思置信度
  "runs_seen": 3                          // 跨 run 出现次数（Consolidation）
}

用途：

  • 注入生成 prompt：「点击此按钮进入站点选择页」→ 生成的代码行为与真实 UI 对齐
  • 遍历跳过死路：已知死路/危险按钮直接跳过（比 _RISKY_TEXT 黑名单精确得多）
  • 指令合成：元素文档 → 低阶指令（「点击设置按钮」）→ 高阶任务（「修改 Wi-Fi 密码」）

工作量：中，蒸馏脚本 + LLM 调用 + Consolidation 逻辑。

4.2.6 InstructionSynthesizer（指令合成 / 数据工厂）

目标：⟨s, a, s'⟩ 三元组 → 低阶指令 → 高阶任务 → 训练/评测数据（OS-Genesis 路线）。

流程：

三元组 (before_screenshot, action, after_screenshot)
  │
  ├─► 低阶指令合成 (LLM)
  │   "点击屏幕上的'设置'按钮"
  │
  ├─► 高阶任务合成 (LLM, 串联多个低阶指令)
  │   "进入设置并修改 Wi-Fi 密码"
  │
  ├─► 轨迹奖励模型 (TRM) 质量过滤
  │   completion score + coherence score
  │
  └─► instructions.jsonl (训练数据导出)

战略价值：把采集管线升级成数据工厂，匹配 fork 的国产模型定位。

工作量：大（战略级），需多轮 LLM 调用 + TRM 评估。

7.2 Sprint 详细设计

S1 · 数据集基线（1 天）

目标：用已验证的 3 个 seed run（launcher / settings / fileexplore）合并出首个可用数据集。

步骤：

  1. 写 merge_graphs.py：读 3 份 graph.json → 签名去重合并 → global_graph.json
  2. 统计覆盖率：目标 App 界面数 / 唯一边数 / 悬空状态数
  3. 生成 HTML 覆盖率报告：状态缩略图墙 + UTG 拓扑图
  4. 质量门：零悬空 + 目标 App 全覆盖

验收标准：≥ 10 个真实状态（captured=True），0 条悬空边，3 个目标 App 均覆盖。

S2 · 感知增强（1.5 天）

目标：SoM 标注导出 + pHash 第二签名通道。

  1. SoM 导出（半天）：新建 som_exporter.py，Pillow 在 768px JPEG 上画框 + 编号，产出 screenshot_som.jpg
  2. pHash 通道（1 天）：meta.json 加 phash 字段；去重规则升级为「结构签名相同 且 pHash 汉明距离 ≤ 8 → 同状态」
  3. 回放所有已有 state 补算 pHash
  4. 新增 3 个单测：SoM 位置正确性 / pHash 一致性 / 近重复检测

验收标准：每个 state 目录含 screenshot_som.jpg + meta.json 有 phash 字段；pytest ≥ 32。

S3 · 跨 run 记忆（1 天）

目标：GlobalUTG 模块，遍历启动时加载，已探过的边不重复探索。

  1. 新建 global_utg.py：GlobalUTG 类 + merge_run() + has_edge()
  2. 遍历器启动时 global_utg.load()，_explore 中查 has_edge(sig, action.key) → 跳过已知边
  3. 遍历结束后 global_utg.merge_run(graph) + save()
  4. 新增 --incremental CLI 参数
  5. 新增 2 个单测：合并正确性 / 增量跳过

验收标准：第二次遍历同 App 状态数 ≤ 首次的 30%；global_graph.json 随 run 增长。

S4 · 元素文档库（2 天）

目标：UTG 边蒸馏成 AppAgent 式元素文档，注入生成 prompt。

  1. 新建 element_doc.py：distill(graph) → element_doc.json
  2. element_id ← bounds+class 哈希；action_effect ← to-state texts 摘要（初版无需 LLM）
  3. Consolidation：同一元素跨 run 出现 → 取最新 action_effect
  4. 生成 prompt 注入：在 codegen prompt 中追加「此界面元素的行为文档」段落
  5. 可选：用 doubao vision 生成 visual_description（每 run 人工看 3-5 条）

验收标准：≥ 20 条元素文档；生成代码中按钮行为与真实 UI 对齐率 ≥ 80%。

S5-S6 · M3A + LLM 引导探索（4 天）

目标：从「盲 DFS」升级为「LLM 引导探索」。
