### 关键判断
- abi/screenshot-to-code 在"多栈 + 多模型 + 自托管"维度仍是最强通用底座
- 但单次生成不保证高还原,真要"像素级一致"得叠 micro-agent / imugi / screenshot-to-html 这类视觉 diff 闭环
- 2026 所有工具都做不到 100% 还原,业界共识 70-80% 起步
- Flame-Code-VLM 是唯一走"自研 VLM + 开源权重"路线的,其他都是调用闭源 API

## 修复:screenshot-to-code _get_variant_models bug + WebSocket 主流程对比

### Bug 修复
- **文件**: `backend/routes/generate_code.py`
- **问题**: `_get_variant_models()` 方法 line 492 引用了 `openai_base_url` 变量,但该变量不在方法参数中
- **影响**: 当只有 openai_api_key 且 OPENAI_BASE_URL 指向 volces.com 时,触发 `NameError`,被 `except Exception` 捕获,误报为 "No API key"
- **修复**: 给 `select_models()` 和 `_get_variant_models()` 都添加 `openai_base_url` 参数,调用处传入 `context.extracted_params.openai_base_url`

### WebSocket 主流程 vs 直调流程对比
- **直调流程**: `httpx.post` → Ark API,单次请求,无 Agent 管线,~30s,生成 12,853 chars
- **WebSocket 主流程**: Frontend → ws://7001/generate-code → 6 Middleware → AgentEngine,4 variant 并行,工具调用(save_assets/create_file),~153s,生成 14,597 chars
- **结论**: 两者都完整覆盖源截图所有 UI 组件;直调适合脚本批处理,WebSocket 适合生产环境
- **对比报告**: `e2e_demo/run_20260901/ws_vs_direct_comparison.html` (113KB,自包含)
